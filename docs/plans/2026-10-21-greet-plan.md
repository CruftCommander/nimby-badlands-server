Greet shows a welcome window after a player spawns: server rules, the Discord invite, how to join, the restart schedule, the mod list, and whatever else Jeff puts in it. The text is a JSON file in the server profile folder, written in a markdown subset, in as many languages as Jeff supplies, and fetched by the client after it spawns, so Jeff edits it without a client update. Each client remembers which version it has dismissed, so a returning player sees the window again only when the text changes and Jeff asks for it, or when the player opens it with the hotkey or from the pause menu. Images and short looping clips ship inside the client PBO and are placed by id from the text. The vanilla hourly `messages.xml` lines stay; the per-mod join lines move into the window once Greet is live.

Three constraints follow from the engine and are stated here so nobody expects otherwise: text changes are live (server file), but every image or clip is a Workshop release, because the client must already hold the file inside the PBO (Phase 0 item 9 proved the PBO path loads a `.edds`; G15). ## What this is not

- Not a rules engine. Greet displays text; it enforces nothing and records nothing about who read it.
- Not a replacement for `messages.xml`. The hourly server messages stay vanilla; only the on-connect join lines move into the window, and only at Greet's release.
- Not a motd that nags. A dismissed window never opens by itself again on that client unless Jeff raises `version` with `forceShow` true (G4). The player can always open it with the hotkey or from the pause menu.
- Not a browser. Links open in the player's default browser through `OpenURL` (NIMBY-T-045); Greet renders no web content.
- Not a media channel. Images and clips are release-bound PBO content (G15); the server file only places them. Nothing in Greet plays video: `VideoWidget` is not used anywhere (NIMBY-T-038).
- Not the Menu addon. Greet has one key binding (G7) and the in-window preferences in G16 and G17, stored in its own `$profile:NimbyGreet\prefs.json`; when Menu exists they register with it. Nothing depends on Menu.
- Not a save-footprint change: no entity data, no `OnStoreSave`/`OnStoreLoad`, no persistent class.

| G3 | Text source | `$profile:NimbyGreet\greet.json` on the server, read at mission start and re-read on a client request when the last read is older than `rereadSeconds` (default 10), so an edit takes effect for the next joiner without a restart and a burst of joins costs one read. Each entry at most 1,023 bytes of UTF-8 (the engine's string limit, NIMBY-T-055); 4,000 characters for the joined body. A body written as one string is a validator error; what the server does with one was not measured |

Media (client PBO, `NimbyGreet/Media/`): a still is `<id>.edds`; a clip is `<id>-0.edds` to `<id>-<frames-1>.edds` (at most 8); `id` in `[a-z0-9]` plus `-` but not ending in `-<digit>`, so a still id and a clip's frame names cannot collide. Every file is power-of-two on both sides (G15). All are listed in `Media/manifest.json` as `{ "media": [ { "id", "kind": "still" | "clip", "width", "height", "frames", "frameMs", "source", "license" } ] }` (an object with one array, so the serializer reads a class) so the client sizes the block before the file loads, knows how many frames to request and how fast to flip, and `NOTICE` has one place to read. `frames` is 1 and `frameMs` 0 for a still.

`seen.json` (client, `$profile:NimbyGreet\seen.json`):

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `dismissedVersion` | `integer` | Yes | Version shown when the player last closed with the checkbox on, or the version of a forced open (G4) |
| `neverShow` | `boolean` | Yes | `true` once the checkbox has been used; cleared by closing a manually opened window with the box unticked (G7, Q6) or by deleting the file |

`prefs.json` (client, `$profile:NimbyGreet\prefs.json`): `textScale` (`1.0`, `1.25`, or `1.5`), `playAnimations` (`boolean`), `language` (`string`, empty for detected) (G17).

RPC payloads (`65511xx`):

| Id | Direction | Fields |
| --- | --- | --- |
| `6551101` request | client to server | `requestId` (int, client counter), `language` (string), `dismissedVersion` (int), `neverShow` (bool), `manual` (bool) |
| `6551102` chunk | server to the owning client | `requestId` (int), `index` (int), `text` (string, at most `CHUNK_BYTES` = 1,000 bytes of the serialized `Language` JSON, cut on a character boundary) |
| `6551103` done | server to the owning client | `requestId` (int), `chunkCount` (int, 0 when nothing was sent), `doneJson` (string): a `NimbyGreetDone` record serialized to JSON, carrying `version` (int), `forceShow` (bool), `servedLanguage` (string), `languages` (array of string, for the selector), `openDelaySeconds` (number), `openRetrySeconds` (number), `totalBytes` and `hash` (int, the integrity check Phase 0 proved) and `reason` (string, why nothing was sent: `dismissed`, `no-text`, `cooldown`) with `retryAfterSeconds` (number, with `cooldown`: when the server will answer again). One string instead of a ten-field `Param` so the record can grow without a wire change; it is well under `CHUNK_BYTES` |

Default `greet.json` written on first boot carries `english` only with placeholder sections (`welcome`, `rules`, `discord`, `restarts`) and the restart schedule from `docs/operations/restart-schedule.md` (so a schedule change is a client release for the default text only, which no live server shows past its first boot); the real text is the repository draft (G12), which Jeff reviews and copies to the host at release.
