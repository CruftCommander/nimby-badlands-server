## Findings

- **NIMBY-T-049 (cooldown refusal was silent, G5).** The per-identity rate limit answered a request inside `requestCooldownSeconds` with nothing, so a language switch (or an Insert press) within 5 s of the last fetch left the window waiting on a response that never came; the next click inside the window was refused again. Fixed: the refusal is a `done` with `chunkCount=0`, `reason=cooldown` and `retryAfterSeconds`; the client schedules one retry of the same request after that time (`m_NimbyGreetRetryPending`, cleared by any newer request). The log line `request refused reason=cooldown` stays, once per cooldown. Plan G5 and test G-24 amended.
- **NIMBY-T-050 (mod string table after an in-session language change, G14).** Changing the game language in Options without restarting the client left `Widget.TranslateString` returning the bare keys for Greet's table while vanilla strings switched; after a client restart the German column resolved. Fixed: `NimbyGreetMenu.Tr(key, fallback)` returns the English text when the engine returns a key, so the window degrades to English, never to `STR_` names. The body text was never affected (it comes from the server).
- **NIMBY-T-051 (the spawn open gave up behind the pause menu, G5).** Vanilla opens the pause menu at spawn when the game window is not active (`missionGameplay.c:296-310`: on the first update, `!g_Game.IsAppActive()` queues `Pause()`, which runs once the player is loaded). Greet correctly never draws over it, but it counted that wait toward `openRetrySeconds` and gave up after 30 s (client 07:40:45 to 07:41:17.363, `open deferred` #1 to #120 with `menu=9`, then `open gave up after 120 retries source=spawn menu=9`), so a player who switches windows during a long load and lingers in the pause menu never gets the window on that connection. Jeff, October 26, 2026: time behind the pause menu does not count; other menus keep the limit. Fixed after run 5's first tests in `NimbyGreetRules.OpenWaitCounts` (three self-test cases) and the open loop, which logs the uncounted wait once; `OnMissionFinish` now also removes a queued open from the call queue, since the wait is no longer bounded. Plan G5 amended.
- **NIMBY-T-052 (client crash after a disconnect within 20 s of a request, G5, G-21).** Jeff pressed Insert at 08:42:23.030 (`request sent id=2 manual=true`), logged out to the main menu (`mission finished` 08:42:40.999, `intro.Nasdara` loaded 08:42:41.367) and the client crashed at 08:42:43: `Access violation. Illegal read ... at 0x900000006`, script stack `DayZGame.OnUpdate`, `scripts/3_Game/dayzgame.c:3044`, which is `GetCallQueue(CALL_CATEGORY_GUI).Tick` (`crash_2026-10-26_08-40-39.log`, `DayZ_x64_2026-10-26_08-40-39.RPT`, minidump `DayZ_x64_2026-10-26_08-42-43.mdmp`, copied to `logs\client-run5\`). 08:42:23 plus `FETCH_TIMEOUT_MS` (20 s) is 08:42:43: the fetch give-up queued on `MissionGameplay` fired after the mission object was destroyed. `OnMissionFinish` removed only `NimbyGreetTryOpen` (added in `6393deb`); `NimbyGreetAutoRequest`, `NimbyGreetRetryRequest` and `NimbyGreetFetchTimeout` (`bdbca24`, first built in run 5) were never removed. Earlier disconnects this morning came 25 s and 35 s after the last request, which is why it did not show sooner. Any player leaving within 20 s of a request, or within the cooldown of a refused one, crashed to desktop: release-blocking. First fix (`a382065`): `OnMissionFinish` removed all four and each was queued at most once at a time; G-P1-18 crashed the same way, so `ScriptCallQueue.Remove` on an instance method did not take the call off the queue (whatever the native reason; it is not documented in the 1.30 scripts, `2_GameLib/DayZ/tools.c:52`). Second fix (`2fb2c8e`): static functions in 5_Mission with a connection number; G-P1-19 crashed the same way. Cause: the 5_Mission script module is compiled afresh for every mission (`Module: Mission; loaded 230x files` at each mission start, the main menu included), so any queued call whose function lives in 5_Mission, instance method or static, points into a discarded module once the player leaves; three crashes, three garbage read addresses, one stack. Hands is safe because its static `OnTimeout` lives in 4_World. Third fix: every Greet `CallLater` queues `NimbyGreetDeferred.Fire` in 4_World (`nimbygreet_deferred.c`; not recompiled per mission, the Hands precedent), which reaches the mission through a `NimbyGreetDeferredCall` hook on `MissionBaseWorld` (4_World, `MissionBaseWorld.c:1`); `MissionGameplay` overrides it and drops calls for an earlier connection (`s_Connection`, kept in 4_World so it survives the reload, bumped in `OnInit` and `OnMissionFinish`); every other mission ignores it. A first try hooked the vanilla `Mission` class from 3_Game and failed the build's boot check (`-092027`: `Engine class 'Mission' cannot be modded`). Held: the window's clip timer (`FlipClip`, repeating) is still queued from 5_Mission on the menu instance and must move to the same pattern before any media ships; none ships in release 1. Rule for every addon: never `CallLater` a 5_Mission function.
- **Open delay is the respawn countdown, not the fetch.** The first request after a fresh connect was served in 0.5 s (23:23:56.341 to .859), against 2.6 to 4.1 s in Phase 0. The window still waits for `MENU_LOGIN_TIME` to close (G5), which is what Jeff felt as about 5 s. The retry poll is 250 ms now; the wait itself is by design.
- **Enforce limits met while building:** a concatenation chain of about 19 terms with nested calls fails to compile (`Formula too complex`); every log line is now built in short statements. Any JSON parse failure prints the engine's own `SCRIPT (E): JSON ERROR` even through `JsonSerializer.ReadFromString`, so no self-test case may parse malformed JSON (NIMBY-T-042 widened).
- **Cosmetic, fixed:** table cells did not wrap (run 1); tables sat tight against the next paragraph (run 3).
