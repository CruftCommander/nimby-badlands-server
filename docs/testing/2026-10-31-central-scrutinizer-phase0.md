## Deviations from the recon, as built

- Replay window (review finding 1, `a521807`; replaces the October 31 "duplicates for 300 s" deviation). Per sender per connection the server keeps the highest accepted id, the last 256 accepted ids, and the floor (the lowest id in that set once it is full): an id in the set is a duplicate (refused, no work, one gated line), an id below the floor is `invalid reason=stale`, any other id is accepted, also below the highest. No time-based expiry. Residual, stated for the second pass: an id evicted while a lower id is still in the set lies above the floor and would be accepted again; only an id accepted out of order (the harness's high ids) can be in that place, because a real client's ids rise.
- Harness ids (orchestrator ruling, October 31, 2026, on this seat's question; deviates from the brief's "highest plus one"): the harness forges from the server's highest accepted id on that connection plus 1024, read per identity at the start of each step through `NimbyAdminHighWater` (client half, 3_Game; written only by the server, read only by the harness, no decision reads it). Plus one would have collided with the real client's next ids, which the server drops as duplicates with no result. A run forges at most 127 ids (`SKIP` with a reason line beyond that; the run plans 60), so the 256-id set always keeps real client ids. Audit lines are matched by id, actor Steam64 and run start, because these ids now repeat across runs.
- Denied and invalid audit records: bounded to 30 a minute per BI id (a reconnect no longer refills it) and 120 a minute over all senders, unless the actor holds a role (owner and admin are always recorded); what the caps hold back is counted per Steam64 and written as one `audit.suppressed` record (actor `system`) 60 s after the first. Log lines stay gated at one per 10 s per sender. (`84a6fca`, `6ea46cc`, from the automated security review below.)
- Audit readback (finding 4): only intent records are read back, because they are the only appends whose result gates a state change; result records gate nothing. 1.30 has no seek or file-size call (`1_Core/DayZ/proto/EnSystem.c:397-531`), so the readback reads the whole day file once per intent. A 1,500-byte line reads back whole on 164200 (engine self-test case). The readback proves the record reached the file, not that it survives a crash (R5, a stated limitation). Plan question for the orchestrator: write denied and invalid records to their own day file, so the intent readback reads only admin activity.
- Store shape (finding 8): on 164200 the serializer allocates an array member even when its key is absent (the first fix build adopted `{"version":1}` with only a null sentinel), so the stores also require the collection key at the top level of the text (`HasTopLevelKey`). Tack TK-F9 d had already shown that a missing scalar key keeps its initializer, so `version` starts at the sentinel 0.
- Selection (finding 2): besides "selection cleared: player reconnected" (same BI id, new session) the status line says "selection cleared: player left" when the BI id is gone.
- Log text (finding 7): `Safe` is a superset of the finding: it decodes UTF-8 and also replaces malformed bytes and the format characters that hide or reorder text (`4935842`, `5bad47f`).
- `players.list` answers through the codec only and writes no audit record (a query, not a state change); a denied `players.list` writes its `result=denied` record like any other.
