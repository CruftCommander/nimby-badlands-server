## Deviations from the recon, as built

- Replay window (review finding 1, `a521807`, and re-review finding 1, `97ba30c`; replaces the October 31 "duplicates for 300 s" deviation). Per sender per connection the server keeps the 256 highest accepted ids (not the 256 most recent), the highest of them, and the floor (the lowest id in that set once it is full): an id in the set is a duplicate (refused, no work, one gated line), an id below the floor is `invalid reason=stale`, any other id is accepted, also below the highest. Eviction removes the lowest id, so an evicted id is always below the floor and can never run again, and the floor only rises. No time-based expiry. The `a521807` residual (an id evicted while a lower one was still in the set) is gone.
- Harness ids (orchestrator rulings of October 31 and November 1, 2026; deviates from the brief's "highest plus one"): the harness forges from the server's highest accepted id on that connection plus 1,000,000 (October 31: plus 1024), read per identity at the start of each step through `NimbyAdminHighWater` (client half, 3_Game; written only by the server, read only by the harness, no decision reads it). Plus one would have collided with the real client's next ids, which the server drops as duplicates with no result. A run forges at most 127 ids (`SKIP` with a reason line beyond that; the run plans 60), and the set keeps the highest ids, so the harness ids stay in it and take at most 127 of the 256 slots: the set always keeps real client ids and its floor stays below the client's next id. The harness runs once per server process. Before it forges, it checks id headroom (third-pass finding 14, `05ad7c2`): each identity's highest plus 2 x (1,000,000 + 127) must fit a positive 32-bit int, or the run prints `SKIP admin: id headroom` and forges nothing. Two, not one as in the ruling's formula, because each identity reads a new base in two steps and the second base includes the first step's ids; a step that loses headroom mid-run stops the run the same way. Audit lines are matched by id, actor Steam64 and run start, in both audit files, because these ids repeat across runs.
- Denied and invalid audit records: bounded to 30 a minute per BI id (a reconnect no longer refills it) and 120 a minute over all senders, unless the actor holds a role (owner and admin are always recorded); what the caps hold back is counted per Steam64 and written as one `audit.suppressed` record (actor `system`) 60 s after the first; the counts are cleared only after that append succeeded, and a failed append keeps them and retries 60 s later with a `summary deferred` line (re-review finding 12, `e00b647`). Log lines stay gated at one per 10 s per sender. (`84a6fca`, `6ea46cc`, from the automated security review below.)
- Audit readback (finding 4): only intent records are read back, because they are the only appends whose result gates a state change; result records gate nothing. 1.30 has no seek or file-size call (`1_Core/DayZ/proto/EnSystem.c:397-531`), so the readback reads the whole command day file once per intent. A 1,500-byte line reads back whole on 164200 (engine self-test case). The readback proves the record reached the file, not that it survives a crash (R5, a stated limitation). The plan question raised here (a separate day file for denied and invalid records) became re-review finding 13 and is done: Plan 3 v0.9, two audit files, below.
- Audit files (re-review finding 13, `967dd32`, Plan 3 v0.9): `audit-<YYYY-MM-DD>.log` holds the intent and result records of executed commands and the bootstrap system records; `audit-denied-<YYYY-MM-DD>.log` holds denied and invalid records and the `audit.suppressed` summaries; same JSON shape. An intent always goes to the first file, so the readback never reads traffic a non-admin can drive.
- Role sync (re-review finding 6, `4c53391`): a repeated hello with the same role writes no line at all, debug mode included; the `role sync repeated` debug line is gone.
- Store recovery (re-review finding 3, `8329297`, and its third-pass residual, `e31ba54`): a store that ever loaded a file or went through any recovery (also one that ended with source `none`) is never a first install again, so a backup that disappears after a `.lkg` recovery keeps edits refused and never writes the bootstrap owner file.
- Store shape (finding 8): on 164200 the serializer allocates an array member even when its key is absent (the first fix build adopted `{"version":1}` with only a null sentinel), so the stores also require the collection key at the top level of the text (`HasTopLevelKey`). Tack TK-F9 d had already shown that a missing scalar key keeps its initializer, so `version` starts at the sentinel 0.
- Selection (finding 2): besides "selection cleared: player reconnected" (same BI id, new session) the status line says "selection cleared: player left" when the BI id is gone.
- Log text (finding 7): `Safe` is a superset of the finding: it decodes UTF-8 and also replaces malformed bytes and the format characters that hide or reorder text (`4935842`, `5bad47f`).
- `players.list` answers through the codec only and writes no audit record (a query, not a state change); a denied `players.list` writes its `result=denied` record like any other.

## Operations notes

- Audit files (Plan 3 v0.9): per UTC day under `$profile:NimbyAdmin\audit\`, `audit-<YYYY-MM-DD>.log` is the command trail (intent then result per executed command, plus the bootstrap system records) and `audit-denied-<YYYY-MM-DD>.log` is who was refused and why (denied and invalid records, and `audit.suppressed` summaries). Same JSON shape, one object per line. Back up and rotate both together.
- To follow one command, read its `id` in the command file; a refused request has no `intent` and appears only in the denied file.
- A `summary deferred` line in the script log means an `audit.suppressed` record could not be appended; the counts are kept and the summary is retried every 60 s until it is written.
- `audit unavailable` and `audit available again` are written once per file per outage, so a failure of the denied file alone does not block commands (only the command file gates them).
