## Findings

- Sticky toast. "Ears / Earplugs out" stayed on screen for the rest of the client session, through toggles, menus, and leaving the server. Root cause is vanilla: `NotificationUI.RemoveNotification` (`3_Game/DayZ/Client/Notifications/NotificationUI.c:79`) keys the fade map by `m_WidgetTimers.Count() + data.GetTime()`; every Ears toast has `show_time` 3, so with one toast still fading (3 s shown in 1 s ticks, 3 s fade) a later toast can repeat an existing key, `map.Insert` refuses it, and that widget is never faded or deleted. `NotificationUI` is owned by `DayZGame`, so the leak outlives the mission. Ruled by Jeff, October 17, 2026: keep the toast (E4) and fix the leak; `Scripts/3_Game/nimbyearplugs_notificationui.c` overrides `RemoveNotification` with a serial key. Moves to a shared NIMBY base addon when a second mod needs it. Rebuild `@NIMBY-20261017-173032` verified: 12 toggles in four seconds (17:44:48-52), every toast faded.
- No NIMBY tab in Controls (row 4e). The `others` sorting from the rebuild was ignored too: 1.30 does not honor `<sorting>` from `modded_inputs`. Bindings stay under Unsorted until the Menu addon.
- Client `$profile:` is `%LOCALAPPDATA%\DayZ`. The flag path in this record and in plan E10 said `Documents\DayZ`; corrected. The debug lines (toggle, menu, RESET, sample, respawn) are captured in the rebuild test with the flag in the right place.
- E9 evidence: across inventory, pause, Options Sound (open, and slider plus Apply), and Controls, no reset occurred and no reapply fired. The once-per-second sampler never had work to do; it stays as the safety net unless Jeff rules otherwise.
- Server side: `testserver-20261017-152817` ended DONE with 0 `[NIMBY]` events, as expected for a client-only mod; server RPT clean apart from the known live warnings (`NO VALID SPAWNS`).
